# 星衡精密 · 质量追溯与缺陷归因系统 需求分析方案

版本 V1.0 ｜ 日期 2026-11-06 ｜ 密级：项目内部 ｜ 编制依据：六岗位访谈（f00–f55）、业务需求发现报告、同行方案调研、现有需求清单与验收对照

## 〇、文档定位与阅读指引

本文回答四个问题，四者互为闭环：

1. **痛点在哪**——每条痛点必须挂到访谈事实编号，没有事实编号的只能进"待验证"。
2. **AI 能做哪些改造**——明确 AI 承担什么、人不承担什么，并给出优先级与依据。
3. **做什么、不做什么**——需求的规格与边界，含功能需求、非功能需求与红线清单。
4. **怎么算做完**——验收标准清单，每条可观测、可复现、有证据文件。

编号规则：痛点 `PT-xx`、AI 改造点 `AI-xx`、功能需求 `REQ-F-xx`、非功能需求 `REQ-N-xx`、验收项 `AC-x-xx`、缺口 `GAP-xx`。状态标记只有三种：✅ 已实现 / 🟡 部分实现 / ⬜ 未实现。

## 一、分析范围与方法

### 1.1 分析对象

以星衡精密的一次具体事件"返工之前的那张检测表"为样本，覆盖六个岗位：质量总监顾明岚、质检员林亦舟、工艺工程师唐映秋、质量数据工程师秦芮、产品安全负责人傅景、客户质量经理叶书。共采集 36 条事实，编号 f00–f55（非连续编号），作为本方案唯一的证据底座。

需要先说明一个前提：**访谈覆盖率 100% 不等于需求已确认**。本方案中凡涉及数量、比例、时长的表述，未取得样本的一律标注"待样本验证"，不得在验收中使用。

### 1.2 四来源收敛

| 来源 | 代表 | 状态 | 指向的瓶颈 |
| --- | --- | --- | --- |
| Buyer 业务决策者 | 顾明岚 | 已采集陈述，目标与预算待确认 | 定位慢是返工压不下去的根子（f00、f01） |
| Brief 书面需求 | 客户简报 | 仅有场景开场，版本待补 | 优先环节、验收标准、权限边界均未定 |
| Operator 一线使用者 | 林亦舟 | 已采集现场陈述，待样本核实 | 判定之后的手写再录入与核对（f10、f12） |
| Industry 行业可行性 | 同行调研 | 已完成调研，本项目适用性待验证 | 追溯侧成熟、归因侧空白，归因应做成流程而非模型 |

四来源收敛结论一致：**瓶颈不在"是否用 AI"，而在追溯链的数据完整性与责任交接**。这条结论决定了后面所有 AI 改造点都必须围绕"数据能不能用、链路能不能闭合"展开，而不是围绕"模型能不能判得准"。

### 1.3 三条分析路径

**路径 A · 流程拆解。** 按首件检验 → 巡检 → 不合格隔离 → 原因分析 → 返工 → 复检六节点拆解（f01、f20），对每个节点记录触发、输入、输出、责任人、交接对象与失败方式。拆解目的是找出"哪一步的判断可以交给规则、哪一步必须留给人"，而不是画流程图。

**路径 B · 价值与不可逆风险矩阵。** 对候选切入点分别评估四项：改善的业务结果、现状基线、失败何时被谁看见、能否在损害前拦截或事后撤销。**模型置信度不等于业务风险**——放行、根因认定、对外承诺这三类动作即使置信度 99% 也必须保留人工签核。

**路径 C · 证据到需求。** 事实编号 → 痛点 → AI 改造点 → 需求规格 → 验收项，这条链路即第五章的追溯矩阵。任何一环断裂（例如某条需求找不到事实依据、某个痛点没有验收项），都要在缺口登记里显式列出，不允许静默遗漏。

### 1.4 分析自身的边界

- 本方案不预设根因、不承诺收益、不代替客户确认权限。
- 预算 18 万元（f03）与决策链"顾明岚推动、傅景可否决、叶书参与验收"（f04）属于项目管理要素，不进入系统功能需求，但会约束改造点的排期与验收主体。
- 行业调研结论只用于判断技术可行性与借鉴数据模型，不作为客户需求的证据。

## 三、AI 改造点与优先级

### 3.1 筛选准则

四条准则，按顺序判断，任一条不满足即降级或不做：

1. **能用规则判定的，不交给模型。** 判异、越界、版本比对、必填校验都是确定性逻辑，可穷举测试，出错可复现。
2. **失败能被看见、能被拦截的优先。** 同一件事，若能做在"提交之前"（如缺漏当场拦截），优先级高于做在"结论之后"。
3. **只读数据就能做的优先。** 现有接口只读（f32），任何需要写回源系统或自动放行的改造，先出范围。
4. **不触碰三条红线**：不自动认定根因、不自动放行、不代替签核（f05、f40、f52）。

### 3.3 AI 的边界与可测指标

"AI 承担"一列只写 AI 真正做的事；"红线"一列写同一环节里绝不由 AI 做的事。这两列是本方案最重要的部分——**边界比能力更能决定项目能不能上线**。

| 编号 | AI 承担 | 红线（不由 AI 做） | 可测指标 |
| --- | --- | --- | --- |
| AI-01 | 按工单与机台自动带出批次号、机台号；必填缺失时阻止提交；草稿暂存并显示最后同步时间 | 不代替质检员判断检测值是否合格 | 缺漏率、单批录入时长 |
| AI-02 | 从一张不良单反查到工单、物料批、供应商，按可疑度排序并给出证据行 | 不判断"就是这批料的问题" | 3 跳内返回、清单完整率 |
| AI-03 | 给原料批次，列出受影响工单与不良件数，并给出覆盖率告警 | 覆盖不足时不宣称"已完成追溯" | 清单与生成器记录对账一致 |
| AI-04 | 返工单强制携带原业务编号，新旧批号双向关联，缺字段即拒绝提交 | 不自行决定换号是否合规 | 换号场景可追到原刀具 |
| AI-05 | 按缺陷发生时刻取当时有效的标准版本；校验单位、公差版本、校准状态、主编号与事件时间；歧义进人工修复队列 | 不自动修复源系统数据 | 版本召回正确率、歧义拦截率 |
| AI-06 | 聚合硬证据（规则命中）与软证据（同批次/同设备/同时段集中度），输出带证据行的候选原因排序 | 不输出"根因已确定"，止于"待验证" | 注入根因能否进 top-3 |
| AI-07 | 依据缺陷描述与历史案例给候选缺陷码，班组长确认后才流转 | 不替班组长确认缺陷码 | 候选命中率、人工改动率 |
| AI-08 | 多版本标准并存时按 as_of 召回当时版本，回答必带引用（文档名 + 版本） | 不把检索内容当事实结论 | 版本召回集合正确、引用覆盖率 |
| AI-09 | 生成 8D 的 D2–D5 草稿，带草稿横幅与版本引用；提交、批准、驳回全流程留痕 | 不代签、不自动批准 | 8D 导出可用、驳回必填理由 |
| AI-10 | 帕累托 ABC、趋势拟合与 EWMA、P 图、X̄-R / I-MR、Nelson 八规则逐点标记 | 不据此判定产品合格与否 | 判异命中与注入一致 |
| AI-11 | 扫描问答记录，命中越界表述、零引用结论、已废止版本引用，支持逐条复核 | 不自动删除或改写历史记录 | 命中可复核、规则可回归 |
| AI-12 | 固定批次分母、排除规则与统计周期；返工件单独标记不重复计数；批次分母与服务侧完成量并列 | 不把同一业务拆成多次成功 | 周报口径可复算 |
| AI-13 | 交接五要素结构化；未确认接手不算完成；超时升级 | 不以"已发送通知"代替完成 | 交接完整率、超时升级次数 |
| AI-14 | 编码判定、表头别名映射、部分成功报告、CSV 注入防护、零依赖 XLSX 导出 | 不静默丢弃失败行 | 导入失败行可定位 |
| AI-15 | GR&R 双算法、ndc、偏倚线性稳定性；产线数据改做人员读数一致性检查 | 不用产线单次测量硬算 GR&R | 判定与标准一致 |
| AI-16 | 按批次、缺陷率、可疑度汇总供应商表现 | 不自动决定供应商去留 | 与批次数据可对账 |
| AI-17 | 仅存图像路径，不做识别 | 不做端到端视觉检测 | 不适用 |

## 四、需求边界与规格

### 4.1 范围红线

| 做 | 不做 |
| --- | --- |
| 异常定位辅助与追溯清单（f05、f52） | 自动认定根因、自动放行 |
| 批次级 + 工序事件级追溯 | 单件序列号全量谱系（仅预留字段） |
| 按缺陷发生时刻取当时的标准版本 | 用当前版本回答历史问题 |
| 证据包 + 疑似原因排序 + 8D 草稿 | 端到端视觉缺陷检测 |
| 三角色 RBAC + 数据级过滤 + 追加式审计 | 供应商外部账号与多租户 |
| 历史回放验证 → 4 周并行试点 | 直接替换现有业务系统 |

### 4.4 明确不做

不做通用 MES（排产、库存、财务）；不做单件序列号全量谱系；不做视觉缺陷检测；不做 8D 在线审批闭环（只出草稿）；不做供应商外部协同与多租户；不做自动定责与概率置信度产品化；不做流式实时告警；不做规则随工艺版本自动演进。

三条不可让步的硬约束贯穿全部需求：**只给假设不给结论**（措辞层强制）、**as_of 是硬闸**（检索层过滤）、**权限在数据层而非路由层**（越权绕道已在实现中修过一例：班组长经看板参数取走控制图）。

## 七、需求管理与变更

**优先级变更的三种触发**：一是基线数据到位（如缺漏率实测远低于预期，AI-01 可降级）；二是试点反馈连续两周指向同一误判模式（升级对应改造点）；三是红线否决（傅景以关键风险否决，则相关需求立即冻结并复盘，不得绕过）。

**变更流程**：提出变更 → 影响分析（涉及哪些需求、验收项、矩阵行）→ 更新矩阵与验收清单 → 质量总监签字 → 进入下一迭代。清单外需求累计超过合同额 20% 触发重谈。

**版本记录**：V1.0 为首次成文，基于 36 条事实与现有实现状态；后续每次试点复测后升版，并保留旧版以支持审计重建。
