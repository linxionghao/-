# 制造业质量追溯与缺陷归因 · 同行方案调研报告

**调研主题**：制造业质量追溯（Traceability）与缺陷归因（Defect Attribution / RCA）方向的开源同行方案

**检索平台**：GitHub、Gitee、arXiv、IEEE Xplore、ScienceDirect

**时间窗口**：优先收录 2024—2026 年创建或仍在活跃维护的项目

**数据时点**：2026 年 10 月（星标数、最近提交时间为采集时点快照）

---

## 一、摘要

1. **"追溯"这一半已有成熟的开源工程实现**，可以直接借鉴数据模型与交互设计；"缺陷归因"这一半在开源世界里几乎没有成品，只有研究代码与商业 QMS 的 CAPA/8D 模块。
2. 2024—2026 年该赛道新增仓库数量不少，但**绝大多数是 0—5 星的一次性作业或演示仓库**，真正具备工程厚度的不超过四个：carbon、hipi-trace、Ingot、causRCA。
3. **最贴近本项目题目的是 Ingot**（开源工艺追因与优化系统）。它的核心判断值得直接吸收：归因不是一键出答案，而是把真实运行数据变成可追溯的证据，再由工程师验证原因。
4. **唯一可用的归因评测口径是 causRCA**。多数同类项目只演示不评测，能回答"我的归因准不准"本身就是竞争力。
5. 该方向真正的行业标准是 **8D、5Why、鱼骨图（Ishikawa）、FTA**，以及 IATF 16949 对标识与可追溯性的强制条款。系统应当输出结构化证据与假设，最终归因由人签字确认。

## 三、总体判断：一半成熟，一半空白

**追溯侧成熟。** ERP/MES/QMS 类开源项目已有完整实现，批次与序列号谱系、正向/反向查询、质量围堵（containment）范围计算都有现成参考。技术含量集中在数据模型，而非算法。

**归因侧空白。** 真正的缺陷归因需要"工艺参数 + 设备状态 + 批次谱系 + 检验结果"四路数据在时间轴上对齐，这类数据不会公开。因此工业界把归因放在商业 QMS 的 CAPA/8D 流程模块里，卖的是流程规范而不是算法。开源社区留下的基本是论文配套代码。

**噪声极大。** 2026 年出现了大量名称里带"quality traceability""rca agent""AetherMES"的仓库，星标为 0—1，内容多为骨架代码或 AI 生成的目录结构。这类仓库只能作为"同题作业对照"，不能作为方案依据。

**因此本项目的合理定位是**：不做通用 MES，而做"追溯 + 归因"的窄而深闭环——输入一张不良品单与批次号，输出关联对象、疑似原因排序与证据、影响范围清单、8D 草稿。

### 4.2 头部方案点评

**crbnos/carbon —— 唯一可当参照系的完整实现**

开源 ERP + MES + QMS，把报价、MRP、库存、车间、质量与批次/序列号追溯压在同一套 Postgres schema 上，并提供 REST API 与 MCP server。它的价值不在于代码可复用（许可证是自定义条款，不能直接抄），而在于证明了"追溯不能脱离生产上下文"这一设计原则：质量记录与工单、工艺路线同源，才能回答"这个不良品是在哪道工序、用哪批料、哪台设备做出来的"。

- 可借鉴：批次/序列号谱系的数据组织、质量模块与工单的关联方式
- 不可借鉴：代码本体（许可证不明确，商用前必须逐个核实条款）

**HipiCloud/hipi-trace —— 一物一码的编码与流转模型**

Gitee 上最成熟的中文溯源项目，526 星、210 次 fork、GPL-3.0、Java。定位是溯源防伪（快消、种养殖、加工、仓储、零售），把产品生命周期各环节信息留存在系统内。

- 可借鉴：一物一码的码段设计、环节节点建模、扫码事件流
- 注意：GPL-3.0 具有传染性，一旦复制代码，整个仓库都需以 GPL 开源
- 注意：它是"防伪 + 营销"导向，与"制造过程质量"导向不完全一致，工序粒度较粗

**liuweichaox/Ingot —— 与本项目题目重合度最高**

"开源工艺追因与优化系统：把真实运行变成可追溯证据，帮助工程师找差异、验原因、定下一份配方。"技术栈为 C#/.NET + React，后端接 BoTorch 做贝叶斯优化，覆盖 DoE（试验设计）、实验追踪、工艺优化，Apache-2.0 许可，2024-09 创建、2026-10 仍在提交。

- 可借鉴：**归因的三段式工作流**——找差异（对比良品/不良品批次）、验原因（设计实验或查历史）、定方案（下一份工艺配方）
- 可借鉴：把"证据"作为一等对象存储，而非只存结论
- 注意：它面向流程工业（配方/参数），离散制造的工单/工序模型需自行补齐

**haishikeji/GC-SPC-QCSC —— 国产 SPC 的功能清单参考**

SPC 统计过程管理系统，覆盖基础数据、物料与供应商、检测模板与记录、检测数据管理、质量分析、不合格品追踪、大屏看板与钉钉推送。

- 可借鉴：检测模板（动态检验项）的数据结构、不合格品追踪的状态流转
- 注意：代码为单次提交后未再更新，工程完整度未知，许可证未声明

### 4.3 新近项目点评

**Open-Factory-Initiative/Factory-Intelligence-Platform（2026-05 创建）**
面向质量漂移检测、合成工厂仿真与受治理的 AI 工作流，架构上引入 MQTT、OPC-UA、数字孪生、多智能体。星标仅 5、未解决问题 50 个，属于早期项目。

- 价值：看它如何把"AI 工作流"约束在可审计的框架内，与"归因结论必须可追溯"的诉求同构
- 风险：成熟度低，不建议作为实现基础

**statistical-process-control（2026-05 创建）**
不是完整系统，而是 SPC 的工程范式集合：控制图、失控（判异）规则、MES/SCADA 数据接入、告警与合规报告，配套网站 statistical-process-control.org。

- 价值：判异规则（Nelson 规则、Western Electric 规则）是**确定性逻辑**，最适合放进核心层并写单元测试
- 注意：星标 1，未声明许可证

**KarimAmer45/manufacturing-traceability（2026-10 创建）**
PostgreSQL 实现的制造追溯、批次谱系与质量围堵，附带模拟产线与 Bosch 基准。星标 0，但选题与本项目几乎完全重合。

- 价值：**模拟产线 + 注入已知根因**的做法，是在没有真实工厂数据时的标准解法，且"注入的根因能否被找回"天然就是评测指标
- 注意：单人或小组项目，不建议引用其结论，但值得读其表结构

**weijiakang8-dotcom/factory-rca-agent（2026-08 创建）**
Apache-2.0、Python，仓库无描述，星标 1。属于"AI Agent 做 RCA"这一类新尝试，可看思路，不宜作依据。

## 五、归因与算法类

| 来源 | 时间 | 类型 | 可借鉴点 |
|---|---|---|---|
| causalgraph/causRCA | 2025-07 | 数据集 + 评测框架 | 制造系统因果发现与自动 RCA 的基准，定义"什么算归因正确" |
| KG-RAG for Manufacturing Problem-Solving（IEEE） | 2025 | 论文 | 知识图谱 + 检索增强，把老师傅经验结构化为可查询知识 |
| KG + 异常检测做维修 RCA（Eng. Appl. of AI） | 2025 | 论文 | 数据驱动告警与知识图谱推理的融合路线 |
| DoWhy / EconML | 持续维护 | 通用库 | 因果推断的工程化实现，归因环节可直接调用 |

**关键结论：不要试图训练一个"归因模型"。** 工业界认可的归因是流程：先有硬证据（规则越界、判异命中），再有统计线索（同批次/同设备/同时段的集中度），然后是因果假设，最后是人签字确认的根因。算法只在"统计线索"这一层发力。

| 资源 | 时间 | 用途 |

没有公开数据集覆盖"工艺参数 + 批次谱系 + 缺陷记录"的完整链路。可行方案有两条：一是用公开视觉数据集做缺陷检测一侧；二是自造模拟产线并在数据中注入已知根因，用"根因可召回率"作为核心指标。

## 七、商业产品与行业标准（答辩对照系）

开源方案的空白，正是商业产品的位置。SAP QM、Siemens Opcenter Quality、Plex、ETQ Reliance 等系统里，缺陷归因以 **CAPA / 8D 模块**的形式存在，核心不是算法，而是流程规范。

行业通用的归因方法论包括：

- **8D 报告**：D1 组建团队 → D2 描述问题 → D3 临时围堵 → D4 根因分析 → D5 纠正措施 → D6 验证 → D7 预防再发 → D8 表彰
- **5Why**：连续追问为什么，逼近根本原因
- **鱼骨图（Ishikawa）**：从人、机、料、法、环、测六个维度枚举可能原因
- **FTA 故障树**：自上而下演绎失效路径

合规层面，**IATF 16949 第 8.5.2.1 条**对标识与可追溯性有强制要求（汽车行业供应链），这也是质量追溯系统在制造业落地的真实驱动力。部分整车厂的供应商手册甚至明确要求：每份 8D 必须附鱼骨图与 5Why 分析。

对本项目的启示：把 8D 的 D2—D5 做成系统里的结构化流程，比堆砌功能更能体现工程判断力。

## 八、可借鉴的四条结构性设计

**1. 谱系数据模型（抄字段，不抄代码）**

物料批次 → 工单 → 工序 → 设备/工装/操作者 → 检验记录 → 成品序列号。必须同时支持两个方向的查询：正向（这批原料流向了哪些成品，用于围堵）与反向（这个不良品用了哪批料，用于溯源）。

**2. 归因分层，每层证据冻结**

规则命中（SPC 判异、参数越界，硬证据）→ 统计相关（同批次/同设备/同时段的集中度，软证据）→ 因果假设（标注"待验证"）→ 人工确认（记入 8D 根因）。系统只输出到"假设"，最终结论由人签字。这个边界设计比"AI 自动定责"更可信，也更符合工业现场。

**3. "当时的规范"是硬闸**

质量标准、工艺参数上下限都有版本与生效日期。追溯时必须取**缺陷发生时**的版本，而不是今天的版本。版本化规范的查询应按业务时间（as_of）过滤，而非按录入时间。

**4. 把 SPC 判异规则做进核心层**

Nelson 规则、Western Electric 规则是确定性判断，无外部依赖、可穷举测试，是最适合放进核心业务层并配齐单元测试的模块。它同时为归因提供"缺陷前兆"的触发器。

## 十、结论与建议

1. **不要把项目做成 MES 半成品。** 开源世界里 carbon 已经把这件事做到极致，再做一个只会显得单薄。
2. **把重心放在"归因的证据链"上。** 输入不良品单与批次号，输出关联对象、疑似原因排序与证据、影响范围清单、8D 草稿。四步闭环，每一环都能演示、能测试、能评审。
3. **借鉴 Ingot 的工作流，借用 causRCA 的评测口径，照搬 SPC 的判异规则，参考 carbon 的谱系模型。**
4. **诚实标注边界。** 系统给假设，人给结论；数据是模拟产线，评测是注入根因的可召回率。这种"知道自己不知道"的表述，在课程评审里通常比功能数量更能得分。
