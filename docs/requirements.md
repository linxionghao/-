# 需求清单

> 版本 v0.1.0 ｜ 定位：课程项目，单机可演示 ｜ 一句话：**一张不良品单进去，四样东西出来**——关联对象、疑似原因排序、影响范围清单、8D 草稿。

## 一、范围与非目标

| 做 | 不做 |
|---|---|
| 物料批次级追溯 + 工序级事件留痕 | 通用 MES（排产、库存、财务） |
| 正向围堵（料 → 成品）与反向溯源（成品 → 料） | 单件序列号全量谱系 |
| 归因输出「疑似原因 + 证据 + 待验证假设」 | 自动定责、概率置信度产品化 |
| 按缺陷发生时刻取当时的质量标准版本 | 端到端视觉缺陷检测模型 |
| 导出 8D 草稿（Markdown） | 8D 在线审批闭环 |
| 三角色权限 + 追加式审计日志 | 供应商外部账号与多租户 |

## 二、核心数据模型

**统一约定：每条业务记录都存两个时间——`occurred_at`（业务时间，事情何时发生）与 `recorded_at`（录入时间，数据何时进系统）。所有追溯查询走业务时间。**

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `material_lot` 原料批次 | lot_id, supplier_id, material_code, received_at, qty | 追溯的起点 |
| `work_order` 工单 | wo_id, product_code, line_id, planned_qty, started_at | 追溯的骨架 |
| `operation_event` 工序事件 | event_id, wo_id, op_code, equipment_id, operator_id, started_at, params_json, recipe_version | 解冻 / 切粒 / 检品 / 包装 |
| `inspection` 检验记录 | insp_id, wo_id, op_code, inspected_at, sample_qty, defect_qty, spec_version | `spec_version` 指向当时生效的标准 |
| `defect` 缺陷条目 | defect_id, insp_id, defect_code, severity, qty, image_path | 图像仅存路径，不做识别 |
| `spec_version` 标准版本 | spec_id, op_code, param_name, lower, upper, effective_from, effective_to | 生效区间，支持 as_of 查询 |
| `attribution_case` 归因单 | case_id, defect_id, evidence_json, hypotheses_json, status, confirmed_by | `confirmed_by` 非空才算结论 |

关系主线：`material_lot ↔ work_order ↔ operation_event ↔ inspection → defect`。
`defect` 上挂 `attribution_case`，`attribution_case` 必填 `evidence_json`（每条证据可回溯到具体行）。

**归因四层，系统只做到第 3 层：**

| 层 | 内容 | 输出性质 |
|---|---|---|
| L1 规则命中 | SPC 判异（Nelson 规则）+ 参数越界（按 as_of 取标准） | 硬证据 |
| L2 统计相关 | 同批次 / 同设备 / 同时段 / 同班组的缺陷集中度 | 软证据，可排序 |
| L3 因果假设 | 良品与不良品的差异对比 | **必须标注「待验证」** |
| L4 人工确认 | 工程师签字 | 唯一可称「根因」的来源 |

## 三、十个关键决策

| 决策 | 选择 | 付出的代价 |
|---|---|---|
| 追溯粒度 | 批次级 + 工序事件 | 不能精确到单件（预留 serial 字段） |
| 数据来源 | 模拟产线（可注入根因）+ CSV 导入 | 无法宣称经过真实产线验证 |
| 视觉检测 | 不纳入，只存图像路径 | 缺陷类型靠人工标注 |
| 归因边界 | 到「假设」为止，人签字 | 无法演示「一键定位根因」 |
| 实时性 | 同步计算，不做流式 | 无秒级告警能力 |
| 规则来源 | 内置 Nelson 规则 + YAML 阈值 | 规则不随工艺版本自动演进 |
| 时间语义 | 双时间列，查询走业务时间 | 不做到事件溯源级重放 |
| 标准版本 | 版本表 + 生效区间 + as_of 过滤 | 全系统查询都要带时间条件 |
| 角色权限 | 三角色 RBAC + 数据侧过滤 | 无外部供应商协同 |
| 部署验收 | 单机 CLI + 本地 Web + pytest | 不容器化、不多租户 |

## 四、技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.9+ | 与现有骨架一致，CI 覆盖 3.9 / 3.12 |
| 存储 | SQLite（单文件，demo 自动重建） | 零运维，演示前一条命令重建 |
| 配置 | YAML（PyYAML，缺失时回退内置解析） | 已实现，规则阈值放这里 |
| CLI | argparse | 已在 `main.py` 就位 |
| 界面 | 标准库 `http.server` + 单页 HTML（只读看板） | 零依赖演示，复用既有经验 |
| 测试 | pytest（`pythonpath=src` 已配好） | 已有 16 个用例打底 |
| 依赖策略 | 核心零第三方，除 PyYAML | 换机器能跑，答辩不翻车 |

## 五、验收标准

| # | 标准 | 怎么验 |
|---|---|---|
| 1 | 反向溯源：给成品批次，列出所用原料批次、工序、设备、当时标准版本 | 一条查询，3 跳内返回 |
| 2 | 正向围堵：给原料批次，列出受影响成品清单，数量与生成器记录一致 | 与模拟数据对账 |
| 3 | as_of 正确：同一问题在 6 月与 9 月问，返回不同标准版本 | 构造两版标准，双用例 |
| 4 | 规则命中：注入一处参数越界，系统命中并给出证据行 | 单测 + demo 场景 |
| 5 | 归因排序：注入「3 号切刀 14:00 后磨损」，该原因进入 top-3 | 根因召回率按场景统计 |
| 6 | 边界：任何输出不得出现「根因已确定」，只能是「疑似 / 待验证」 | 单测断言关键词不存在 |
| 7 | 测试：`core/` 行覆盖率 ≥ 70% | `pytest --cov` |
| 8 | 一键跑：`python examples/demo.py` 完成一次完整闭环 | CI 冒烟 |

## 六、风险与已知限制

| 风险 | 影响 | 应对 |
|---|---|---|
| 模拟数据太「干净」，规则一命中就等于答案 | 指标虚高、评审质疑 | 加噪声、加干扰批次，保留未命中场景 |
| 批次级粒度答不了单件问题 | 追问时露怯 | 明确「预留 serial 字段」，不当场承诺 |
| 无真实产线验证 | 说服力有限 | README 与答辩口径统一为「课程演示，数据为注入根因的模拟产线」 |
| 8D 只到草稿 | 闭环不完整 | 列入 P1，交付时说明边界 |
| 法规口径（IATF 16949 / HACCP）只作参照 | 不能宣称合规 | 文档写「参考」，不写「满足」 |
