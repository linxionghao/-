## 一、这份手册怎么用

本手册按「**第一次部署 → 日常运行 → 出问题怎么办 → 交付验收**」的顺序编排。三类读者可以只看对应章节：

| 读者 | 建议先读 | 日常需要 |
| --- | --- | --- |
| 运维人员 | 第二、三、四章 | 第六章巡检、第九章故障处理、第十章备份 |
| 质量主管 | 第五章账号权限、第七章数据准备 | 第八章知识库维护、第十一章安全 |
| 班组长 | 第五章角色说明、`/m` 页面操作 | 无（现场录入不需要运维知识） |

**一句话定位**：这是一套「让归因结论可回溯」的系统，不是「自动定责」的系统。它给证据、给候选、给待验证假设，判决权始终在人。

## 二、系统概况

### 2.1 它解决什么

| 痛点 | 系统做法 | 不做什么 |
| --- | --- | --- |
| 检测表手写后漏填批次、机台 | 建单时按工单自动带出，必填缺失阻止提交 | 不代替质检员判断检测值是否合格 |
| 返工换批号后追不到原刀具 | 新旧批号双向关联，缺字段拒绝提交 | 不自行决定换号是否合规 |
| 8D 靠个人记忆和便签 | 归因单固化证据行，审批留痕 | 不输出「根因已确定」 |
| 标准版本混用 | 按缺陷发生时刻取当时有效版本 | 不自动修复源系统数据 |

### 2.2 技术构成

| 层 | 内容 | 规模 |
| --- | --- | --- |
| 接口层 | FastAPI 路由与 JWT 鉴权 | 64 个端点 |
| 编排层 | 契约 / 硬规则 / 模型判断 / 工具调用 / 人工复核 | 5 层，6 个工具 |
| 核心层 | 统计与 SPC、谱系追溯、导入导出、MSA | 53 个模块 |
| 存储 | SQLite（WAL 模式） | 16 张表 |
| 前端 | 原生 HTML/CSS/JS，服务端渲染 | 15 个页面 |

### 2.3 三个角色与三处人工确认点

| 角色 | 标识 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| 班组长 | `shift_leader` | 本线建单、确认缺陷码、查本线工单 | 看控制图、审批归因、看其他产线数据 |
| 质量工程师 | `quality_engineer` | 问答、统计、追溯、归因提交、MSA | 审批归因、改知识库 |
| 质量主管 | `quality_manager` | 全部，含审批、审计核查、知识库管理 | — |

**三处人工确认点（系统硬约束，不是流程建议）**：

1. **缺陷码确认**：机器给候选，班组长点选后才转「待处理」；
2. **归因审批**：工程师提交后必须主管批准或驳回，驳回须填理由；
3. **问答审计核查**：机器标记的风险问答，主管逐条核查并留痕。

> 这三处由 `ToolSpec.requires_review` 声明，不是散在各接口的 `if`。新增需要人工收尾的能力，改契约即可，不必改业务代码。

## 三、环境要求

| 项 | 最低 | 建议 | 说明 |
| --- | --- | --- | --- |
| 操作系统 | Windows 10 / Ubuntu 20.04 | Windows 11 / Ubuntu 22.04 | 已在 Windows 11 实测 |
| Python | 3.9 | 3.11+ | 3.9 已够用，`removeprefix` 等特性要求 3.9+ |
| 内存 | 2 GB | 4 GB | 索引常驻内存，语料大时按 1 万切片约 200 MB 估 |

**依赖安装**：

```bash
pip install -r requirements.txt
# 开发与测试另装
pip install -r requirements-dev.txt
```

> 本项目**无重型前端构建链**，不需要 Node.js、npm、webpack。页面是原生 HTML，改完刷新即生效，这在小团队交付里能省掉一整类问题。

## 四、首次部署

### 4.1 五步走

```bash
# 第 1 步：取代码
git clone <仓库地址> quality-trace && cd quality-trace

# 第 2 步：装依赖
pip install -r requirements.txt

# 第 3 步：灌演示数据（会建表、建账号、造批次与缺陷）
python scripts/seed_demo_data.py

# 第 4 步：建知识库索引（幂等，语料没变可跳过）
python examples/phase1_rag_demo.py --ingest

# 第 5 步：启动
bash scripts/run_server.sh 8000
```

### 4.2 验证部署成功

按顺序检查四项，任何一项失败都不要继续：

| # | 检查 | 预期 | 失败先看 |
| --- | --- | --- | --- |
| 1 | `curl http://127.0.0.1:8000/api/v1/health` | `code=0`，`index_ready=true` | 索引未建 → 重跑第 4 步 |
| 2 | 浏览器打开 http://127.0.0.1:8000/ | 问答页面正常渲染 | 静态目录路径 → 查 `deps.WEB_DIR` |
| 3 | 用 `qe001 / qe001` 登录 | 进入后台 | 账号未灌 → 重跑第 3 步 |
| 4 | 提问「螺纹外径的检验抽样方案」 | 返回带引用的回答 | 索引为空 → 查 `data/phase1_index/` |

### 4.3 目录约定

```
quality-trace/
├── config/          # llm.yaml 等配置（密钥走环境变量，不进仓库）
├── data/            # 运行时数据：trace.db、uploads/、phase1_index/
├── docs/            # 需求、架构、接口、权限、验收、运行手册
├── scripts/         # 启动、灌数据、自动同步、文档生成
├── src/quality_trace/
│   ├── api/         # 路由与鉴权
│   ├── core/        # 业务、统计、编排、知识库
│   ├── web/         # 页面模板
│   └── utils/       # 配置加载
├── test/            # 测试方案与过程文档
└── tests/           # 自动化测试 23 个文件
```

> **`data/` 是运行时目录，可重建但不能丢**。`src/` 下不允许出现运行时数据——历史上曾有路径推导少一级，把知识库上传写进了 `src/data/`，已在 `.gitignore` 加兜底规则。

## 五、配置说明

### 5.1 配置文件

| 文件 | 作用 | 是否入库 |
| --- | --- | --- |
| `config/default.yaml` | 业务配置：谱系方向、上传目录等 | 是 |
| `config/llm.yaml` | 模型与向量服务配置 | 是（不含密钥） |
| `config/local.yaml` | 本机覆盖（含密钥） | **否**，已被 gitignore |

### 5.2 关键环境变量

| 变量 | 作用 | 不配的后果 |
| --- | --- | --- |
| `QT_LLM_API_KEY` | 大模型密钥 | 问答降级为 `bm25_only`，返回检索材料 |
| `QT_EMBEDDING_API_KEY` | 向量服务密钥 | 向量通道关闭，仅关键词检索 |
| `QT_JWT_SECRET` | 令牌签名密钥 | 用默认值，**存在伪造令牌风险** |

### 5.3 配置优先级

```
环境变量 > config/local.yaml > config/llm.yaml > config/default.yaml > 代码默认值
```

改完配置必须重启服务，本项目不做热加载——热加载的复杂度换不来收益，反而会让「改没改生效」变成排查难题。

## 六、日常巡检

### 6.1 每日（5 分钟）

| 检查 | 方法 | 正常 | 异常处理 |
| --- | --- | --- | --- |
| 服务存活 | 打开 `/api/v1/health` | `code=0` | 看进程与日志 |
| 是否有降级 | 健康检查里 `llm_key_ready` | 按配置应为 true | 密钥失效或网络不通 |
| 待办积压 | `/admin` 首页待审数量 | 个位数 | 超 20 条说明审批跟不上 |
| 磁盘余量 | `df -h` 或资源管理器 | 剩余 > 20% | 清理 `data/uploads` 旧图片 |

### 6.2 每周

- 导出一次缺陷单与归因单（`/api/v1/io/export?dataset=defects`），人工抽查 5 条，看证据行是否对得上源头数据；
- 检查审计列表里被标记的问答，确认都已核查（`reviewed_by` 非空）；
- 跑一次全量测试：`pytest`，应为 714 通过 / 17 跳过。**数字变了要查原因**，不能当作随机波动。

### 6.3 每月

- 备份数据库并做一次恢复演练（见第十章）；
- 复核知识库版本：过期标准及时下架，但**不可删除**，只能标记失效——历史问答的引用要能回溯到当时的版本；
- 复核账号：离职人员账号立即停用，不要等下次巡检。

## 七、数据准备与导入

### 7.1 四类可导入数据集

| 数据集 | 用途 | 关键字段 | 注意事项 |
| --- | --- | --- | --- |
| `work_orders` | 工单 | 工单号、产品、产线、计划数量 | 工单号是主键，重复导入会跳过而非报错 |
| `defect_codes` | 缺陷码字典 | 缺陷码、名称、分类、关键词 | 关键词用顿号分隔，归一化时按它匹配候选 |
| `lots` | 物料批 | 批号、物料编码、供应商、供应商批号 | 供应商批号是对外追溯锚点，能填就填 |
| `measurements` | 实测值 | 检验项目、数值、产线、子组号、上下限 | 同一抽检的 5 件用同一子组号；超差值也要导，那是事实 |

### 7.2 导入流程

```
上传 → 预览（只校验不落库）→ 确认导入 → 查看部分成功报告
```

**必须走预览**。预览会报出：编码识别结果、表头映射到的字段、失败行与原因。直接导入会跳过这道检查，出错后只能靠比对原始文件排查。

### 7.3 常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 中文乱码 | 文件是 GBK 但被当 UTF-8 读 | 系统会嗅探编码，若仍乱码，用记事本另存为 UTF-8 |
| 表头识别不到 | 列名不在别名表里 | 改成标准列名，或在 `importer` 的别名表里补 |
| 部分行失败 | 类型不符（数值列填了文字） | 看预览的失败原因，逐行修 |
| 导入了但统计没变 | 统计按日期过滤，导入数据日期不在区间 | 检查查询的 `date_from` / `date_to` |

## 八、知识库维护

### 8.1 上传文档

后台 `/admin/documents` 上传，支持 Markdown 与 PDF。上传后自动切片、建索引。

**切片规则**：按标题层级切，单切片不超过设定长度。条款号与版本从文档头部的元信息读，缺失会导致版本闸失效——**这是最容易忽略的一步**。

### 8.2 版本管理

| 场景 | 做法 |
| --- | --- |
| 标准升版（v2 → v3） | 上传 v3，v2 保留并标记失效。不要覆盖 |
| 错别字修正 | 同版本号内容更新，会记录历史版本 |
| 下架 | 标记失效，不删除。已发生的问答仍需能引用到它 |

**为什么不能删**：三个月后有人问「当时为什么这么判」，答案要能指回当时有效的标准。删掉就等于把证据链剪断。

### 8.3 索引重建

```bash
python examples/phase1_rag_demo.py --ingest
```

语料变更后必须重跑，否则新文档检索不到。重建是幂等的，可以随时执行，耗时与语料规模成正比。

## 九、故障处理

按「现象 → 先查什么 → 怎么修」编排。六类异常与测试用例编号对应（见《MVP 测试方案》第五章）。

### 9.1 服务起不来

| 现象 | 先查 | 处理 |
| --- | --- | --- |
| 端口被占用 | `netstat -ano \| findstr :8000` | 换端口或杀掉占用进程 |
| `ModuleNotFoundError` | 是否设了 `PYTHONPATH=src` | `set PYTHONPATH=src` 后重启 |
| 数据库锁 | 是否有残留进程持有 `trace.db-wal` | 关掉所有实例后重启 |
| 索引加载失败 | `data/phase1_index/chunks.json` 是否存在 | 重跑 `--ingest` |

### 9.2 问答没有回答，只有材料

**这不是故障**。健康检查里 `llm_key_ready=false` 时，系统走关键词单通道，返回检索材料与引用，并在响应里标 `degraded=50002`。

处理：配 `QT_LLM_API_KEY` 后重启。**不要**把它当故障上报——否则没配密钥的试点环境会一直报"故障"。

### 9.3 归因提交后一直待审

| 可能 | 查法 |
| --- | --- |
| 主管没收到通知 | 系统不发通知，靠 `/admin` 首页待办计数 |
| 状态机卡住 | 查 `attribution_order.status`，应为 `submitted` |
| 提交失败但界面没提示 | 查审计记录里该请求的 `error_code` |

### 9.4 权限相关

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 班组长看不到控制图 | 设计如此 | 需要看就让主管导出 |
| 40301 | 角色不对 | 找管理员改角色 |
| 40302 | 数据级越权，产线不匹配 | 确认工单归属，不是改权限能解决的 |
| 登录后立刻失效 | 令牌过期或签名密钥变了 | 重新登录；批量失效说明密钥被换过 |

### 9.5 导入失败

先看预览报告，不要直接看最终报错。预览会明确说「第 N 行第 M 列类型不符」，最终报错只给一句「导入失败」。

### 9.6 数据库异常

| 现象 | 处理 |
| --- | --- |
| `database is locked` | 减少并发写入；确认没有多个服务实例共用一个库 |
| 文件损坏 | 从备份恢复（第十章），用 `PRAGMA integrity_check` 先确认 |
| 磁盘满 | 清理 `data/uploads/photos` 里的旧图片，或扩容 |

## 十、备份与恢复

### 10.1 备份什么

| 项 | 路径 | 频率 | 说明 |
| --- | --- | --- | --- |
| 数据库 | `data/trace.db` | 每日 | 含全部业务数据 |
| 上传图片 | `data/uploads/` | 每周 | 缺陷照片，体积大但不可重建 |
| 知识库语料 | `data/knowledge/` | 变更时 | 文档原件 |
| 配置 | `config/` | 变更时 | 含模型配置 |
| 索引 | `data/phase1_index/` | 不必备 | 可从语料重建 |

### 10.2 备份命令

```bash
# 停服后直接拷贝最稳；不停服时用 SQLite 在线备份
sqlite3 data/trace.db ".backup 'backup/trace-$(date +%F).db'"

# 图片目录
tar -czf backup/uploads-$(date +%F).tar.gz data/uploads
```

### 10.3 恢复步骤

```bash
# 1. 停服务
# 2. 备份当前库（防止恢复错了没退路）
mv data/trace.db data/trace.db.bak
# 3. 恢复
cp backup/trace-2026-11-06.db data/trace.db
# 4. 校验完整性
sqlite3 data/trace.db "PRAGMA integrity_check;"
# 5. 启动并验证
```

**恢复后必做**：抽查 3 条缺陷单的证据行，确认关联的实测值、批次还在。数据库能打开不等于数据完整。

## 十一、安全与合规

### 11.1 上线前必须做的五件事

1. **改掉演示口令**：`qe001/qe001` 这类口令必须全部重置；
2. **换掉 JWT 密钥**：默认值在代码里，用 `QT_JWT_SECRET` 覆盖；
3. **关闭 `/docs`**：公网暴露会泄露全部端点结构；
4. **配置 HTTPS**：局域网明文传输时，令牌可被抓包获取；
5. **确认语料授权**：接入企业标准前确认可公开范围，不要直接把客户图纸参数传进知识库。

### 11.2 数据分级

| 级别 | 内容 | 要求 |
| --- | --- | --- |
| 敏感 | 客户名称、供应商批号、工艺参数 | 不出内网，导出需审批 |
| 内部 | 缺陷单、归因结论、实测值 | 按角色隔离，导出留痕 |
| 可公开 | 通用检验标准、8D 方法论 | 可进知识库 |

### 11.3 审计留痕

系统记录的关键字段：请求号、操作人、角色、判定结论、是否转人工、是否降级、错误码、耗时、时间戳。

**不能删**。审计记录是出了质量事故后复盘责任的唯一依据，删除等于自毁证据。

## 十二、升级与回滚

### 12.1 升级步骤

```bash
# 1. 备份（必须）
sqlite3 data/trace.db ".backup 'backup/pre-upgrade.db'"
# 2. 拉取新版本
git pull
# 3. 装依赖（可能新增）
pip install -r requirements.txt
# 4. 跑测试（必须全绿才继续）
pytest
# 5. 重建索引（若知识库模块有变）
python examples/phase1_rag_demo.py --ingest
# 6. 重启服务
```

### 12.2 回滚

```bash
git checkout <上一个版本 tag>
cp backup/pre-upgrade.db data/trace.db
# 重启
```

**注意**：如果新版本改过表结构，回滚数据库是必须的。`db.py` 的建表是 `IF NOT EXISTS`，不做迁移，所以**旧版本读新库可能出错**。

## 十四、已知限制

交付时如实说明，避免上线后被当作缺陷：

| 限制 | 影响 | 何时解决 |
| --- | --- | --- |
| 单进程 + SQLite | 并发写入超 20 人会变慢 | 多实例部署时换 PostgreSQL |
| 设备与工艺参数未接入 | 归因无法自动排到机台级 | 试点二期补数据接口 |
| 归因前三命中率未量化 | 无法承诺排序准确率 | 需试点标注数据 |
| 无消息通知 | 待审任务靠页面查看 | 二期接企业微信 |
| 无热配置加载 | 改配置需重启 | 有意为之，不做 |
