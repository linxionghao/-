## 逐条说明

### #1 反向溯源（🟡 部分达成）

需求原文：给成品批次，列出所用原料批次、工序、设备、当时标准版本。

**已做到**：`GET /genealogy/defects/{no}/backward` 从一条不良单反查到
工单 → 物料批 → 供应商，并对批做**可疑度排序**（依据"该批还进了多少张别的工单"）；
每一批都带 `lot_id` / `supplier` / `op_code`（工序）与领料量。
标准版本那一段走的是另一条链：`defect_item → attribution_order → chat_message_citation`，
每个引用都带 `(doc_name, version)`。

```bash
curl -s "http://127.0.0.1:8000/api/v1/genealogy/defects/DF-DEMO-0007/backward" \
  -H "Authorization: Bearer $QE_TOKEN" \
  | jq '.data.suspects[] | {lot_id, supplier, other_orders, level}'
```

**差在哪**：仍然缺**设备**维度。库里没有设备表，`defect_item` 也不记设备号，
所以"这台机器当时是什么状态"这一跳走不到底。这是本轮唯一没补上的字段级缺口。

**为什么不再等阶段 4**：谱系原来打算留到阶段 4，理由是"粒度定了才能建表"。
实际做下来发现粒度问题只在**单件级**才尖锐；批次级（一批料投多单、一单吃多批）
用 `material_lot` + `lot_consumption` 两张表就够，而且这块表结构在三个查询
（正查、反查、供应商记分卡）都跑过之后才敢说"够用"。
先按批次级建，比继续空着强——**空着的表结构不会因为等待而变得正确**。

返回值里恒定带一句 `caveat`：**相关不等于因果**。同一批料进了 6 张工单只有
1 张出问题，问题更可能在那一张的工艺参数上，而不是这批料上。

### #2 正向围堵（✅ 已达成）

需求原文：给原料批次，列出受影响成品清单，数量与生成器记录一致。

`GET /genealogy/lots/{lot_id}` 给出 批 → 工单 → 不良单 的完整前向影响面，
含每张工单的 `planned_qty`（应产）、不良件数、严重缺陷数，以及汇总的
`total_produced` / `total_pieces`。

```bash
curl -s "http://127.0.0.1:8000/api/v1/genealogy/lots/LOT-20261015-A" \
  -H "Authorization: Bearer $QE_TOKEN" | jq '.data | {orders: (.orders|length), coverage}'
```

**"达成"带一个前提，必须一起说**：这一切依赖领料登记是否完整。
返回结构里 `coverage` 给出"有工单号的不良单比例"，`coverage < 1` 时
结果里会带 `warning`：

> 领料记录不全时，前向追溯**只能说明"查到这些"，不能说明"只有这些"**。

把不完整说成完整，是追溯功能最危险的失败方式——围堵漏掉一张工单，
后果是那批货继续流到客户手里，而系统显示"已完成追溯"。
所以这一条判"达成"是指**功能链路通了**，不是指"任何数据下都可信"；
后者要靠现场把领料登记补齐。

### #2b 数据模型：为什么是多对多而不是树

`material_lot` × `lot_consumption` 是**多对多**：一批料投多张工单，一张工单吃多批料。

```
批 L1 ──┐
批 L2 ──┼── 工单 WO-01 ──┐
        │                ├── 缺陷单 DF-01
批 L3 ──┴── 工单 WO-02 ──┘
```

用树（`parent_id`）建模会在第二张工单上直接撞墙：第二个父会覆盖第一个，
**数据在写入时就错了，而且不报错**。这不是实现选择，是问题本身的结构。
见 [ADR-0009](adr/0009-genealogy-many-to-many.md)。

### #3 as_of 正确（✅ 已达成）

同一问题在不同业务时刻，必须召回**当时有效**的标准版本。这条是本项目两个"陷阱"之一，机制而非提示词：

| 环节 | 实现 |
|---|---|
| 入口 | `POST /api/v1/chat` 的 `as_of` 字段（`YYYY-MM-DD` 或 ISO 时刻），非法格式 → 40001 且提示格式 |
| 检索 | `repo.list_chunks_as_of()` 在 SQL 层过滤 `status='active' AND effective_from <= as_of <= effective_to` |
| 索引外路径 | 走 DB 时 `meta.version_gate = "sql"`，走索引文件时 `"index"`，前端状态条显示当前视角 |
| 前端 | 问答页顶部日期条，清空即回到"当前有效" |

证据：`tests/test_version_gate.py` 9 条，覆盖"v1/v2/v3 三版共存时只召回当时那版"、"as_of 落在所有区间之外 → 0 命中"、"非法 as_of → 40001"。

### #4 规则命中（🟡 部分达成）

需求原文：注入一处参数越界，系统命中并给出证据行。

**已做到**：问答审计的三条规则（`core/services/audit.py`）——`flag_root_cause`（5 组越界表述正则）、`flag_no_citation`（称"完成/已确定"但零引用）、`flag_stale_version`（引用已下架版本）。命中后主管后台可按"仅看命中"筛选并逐条核查，`tests/test_audit.py` 31 条覆盖。

**差在哪**：需求里的"参数越界"指 SPC 意义上的**工艺参数**（如炉温超出控制限），
而不是产品尺寸。Nelson 八条判异准则本身已经实现（`core/analytics/spc.py`，
`test_analytics.py` 94 条覆盖），X̄-R / I-MR / P 图也能给出逐点超限标记，
但**判的是实测值，不是工艺参数**：库里没有 `process_record` 表，
炉温、压力、转速这些量根本没被采集。

这个区别值得说清楚，因为它决定了这一条能不能算达成：
现在系统能回答"这个尺寸失控了"，还回答不了"这台炉子当时超温了"。
后者需要设备直采或至少人工录入工艺参数，属于数据接入问题，不是算法问题。

### #5 归因排序（🟡 部分达成）

**已做到**：归因单的完整生命周期——证据链落库（`evidence_json`）、状态机（`submitted → approved/rejected`，退回必填理由）、8D Markdown 导出（带 `DRAFT` 红条 + 缓存复用）。`tests/test_attribution.py` 11 条。

**差在哪**：L1 规则命中 → L2 统计相关 → L3 假设排序这条**自动排序管线**没有实现。当前归因单的证据由人工构造（或脚本写入），因此"3 号切刀磨损能否进 top-3"无法用系统自动验证——这是需求 #5 的核心，也是阶段 4 归因引擎的主任务。

### #6 边界措辞（✅ 已达成）

任何输出不得出现"根因已确定"，只能是"疑似 / 待验证"。这是**防止 LLM 把检索内容当事实**的落地点，四处强制：

1. `attribution.DRAFT_BANNER`：8D 导出页首行固定插入红字横幅，声明"本文件为草稿，结论待验证"；
2. `attribution_order.hypothesis_text`：写入时即拼上"（待验证）"，导出时不再依赖模型自觉；
3. 班组长侧 `STATUS_TEXT`：只有"待确认缺陷码 / 已提交，待质量工程师判定"，**不出现合格、不合格、判退**等判定词；
4. 单测断言：`assert "根因已确定" not in content`、`assert "合格" not in status_text`。

### #7 覆盖率（✅ 已达成）

`core/` 行覆盖率实测 **91%**（要求 ≥ 70%），整体 `src/` **86%**。命令与逐模块明细见 `docs/test-plan.md` §8，含"为什么 `llm/client.py` 只到 47% 而不去补"的取舍说明。

### #8 一键跑闭环（✅ 已达成）

```bash
python scripts/demo_closed_loop.py        # 加 -v 可看逐条 SSE 事件
```

一条命令、无需起服务、不污染演示数据（临时库 + 临时上传目录，跑完即删）。实测输出：

```
[1] 认证：三个角色各自登录，拿到 JWT                     ✓ ×3
[2] 问答：检索 + 引用（无 LLM Key 时按设计降级）           ✓ 3 条引用 / 降级 50002 如实标注
[3] 版本闸：as_of=2024-06-01 只召回当时有效的标准          ✓ 版本集合 ['v1']；2023-01-01 → 0 命中
[4] 录入：建草稿（带候选码）→ 班组长亲手确认               ✓ draft → pending，响应不含 suggest_json
[5] 归因：提交 → 主管批准 → 导出 8D                       ✓ approved；8D 因无 Key 降级 50002
[6] 审计：扫描问答记录，命中越界/无引用/旧版本             ✓ 扫描 2 条，可逐条核查

闭环完成：15 项通过 / 0 项失败
```

为什么用 TestClient 而不是"起服务再 curl"：

1. 一条命令替代"起服务 + 两个冒烟脚本"，答辩现场不会因为端口被占、后台进程被杀而卡住；
2. 走的是**真实路由 + 真实 SQLite**，只把 ASGI 传输换成内存——鉴权依赖、统一响应包、SSE 事件流都真实执行；
3. 库与上传目录落在临时目录，**不污染** `data/trace.db` 与 `data/uploads/`，可以反复跑。

第 3 步的断言值得单独说：它不看"有没有命中"，而是看**命中的版本集合是不是 `['v1']`**。因为 v2 的文本与问题的相似度更高，如果只靠相似度排序，2024 年那次查询一定会把 2025 年才生效的 v2 捞出来——这正是需求里"三个陷阱"要防的事，所以断言必须落在版本上，而不是条数上。

另外，`examples/demo.py` 保留为阶段 0 的骨架 CLI（`python examples/demo.py` 打印 `ready`），它不是闭环入口，不要混淆。
