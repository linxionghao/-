# 0009. 批次谱系是多对多，不能建成树

- 状态：已采纳
- 日期：2026-11-06
- 影响范围：`core/repo/db.py`（`material_lot` / `lot_consumption`）、`core/services/genealogy.py`、`api/routers/genealogy.py`

## 背景

追溯的经典建模是一棵树：

```
产品
 └ 工单
    └ 物料批
       └ 供应商
```

按这个思路，`material_lot` 上挂一个 `work_order_id` 就够了，
一张工单多个料，一批料对应一张工单。简单、直观、查询只要 JOIN 一次。

问题是真实的车间不是这样：

- 一批 2 吨的钢棒会投到 5 张工单上（分批领用）；
- 一张工单会吃 3 批不同的钢棒（上一批用完了接下一批）；
- 同一批料在同一张工单上可能用两次（粗加工 + 精加工）。

第二行就撞墙了：一批料有两个"父"。用 `parent_id` 建模时，
第二个 `work_order_id` 写进去会覆盖第一个——数据在写的时候就已经错了，
而且**不会报错**。追溯时查到的结果是"这批料只进了 1 张工单"，
一个缺了一半的答案，看起来却是完整的。

## 决策

用关系表建**网状**结构：

```sql
CREATE TABLE material_lot (
    lot_id        TEXT PRIMARY KEY,     -- 内部批号
    supplier      TEXT,
    supplier_lot  TEXT,                 -- 供应商批号
    ...
);

CREATE TABLE lot_consumption (
    lot_id        TEXT NOT NULL,
    work_order_id TEXT NOT NULL,
    op_code       TEXT,                 -- 工序：同批料同单可用两次
    qty_used      REAL NOT NULL DEFAULT 0,
    UNIQUE (lot_id, work_order_id, op_code)
);
```

四个细节：

1. **`supplier_lot` 与 `lot_id` 分开存**。供应商的批号只在他们的体系内唯一，
   两家供应商可能都叫 `20261015A`。混用会让反查时把两家的料算成一批，
   然后把责任判给错误的那家；
2. **`UNIQUE` 带 `op_code`**。同一批料在同一张工单上粗加工用一次、
   精加工用一次，这不是重复记录，是两次领用。去掉 `op_code` 会让第二次
   写入被静默忽略；
3. **`qty_used` 单独记**。只有关系没有数量时，"这批料占该工单用料的比例"
   算不出来，影响面评估就只能按"有/无"给，粒度太粗；
4. **不设 `parent_id`**。这条是刻意写进注释的：以后有人觉得"树更简单"
   时会先看到这里。

反向追溯的可疑度排序依赖"这批料还进了多少张别的工单"：

| 该批出现的其他工单数 | 可疑度 | 逻辑 |
|---|---|---|
| 0（只进了出问题的这一张） | 高 | 问题很可能跟着这批料来 |
| 1–4 | 中 | |
| ≥ 5 且全部正常 | 低 | 更可能是这张工单的偶发因素 |

`min_orders` 参数（默认 2）是必要的护栏：不设阈值时**每一批料都"值得怀疑"**，
排序退化成噪声。

## 后果

- 好处：能表达真实的领用关系；前向追溯可以回答"这批料流到了哪些客户订单"，
  反向追溯可以回答"这张单用了哪些批"。
- 代价：查询要 JOIN 一次关系表，比树模型多一张表；
  折叠成页面要的"批 → 工单 → 缺陷"三列结构需要在服务层做一次归并
  （`build_graph()`）。
- 未来若要改：加入"半成品批"（一批半成品由多批原料合成、又投到多张工单）
  时，`material_lot` 需要加 `parent_lot_id` 或再加一张 `lot_merge` 表，
  但 `lot_consumption` 的结构不用动——网状模型天然支持多层。

## 补充：前向追溯的覆盖率必须报出来

`coverage = 有 work_order_id 的领料记录 / 全部领料记录`。
小于 1 时结果里带 `warning`：

> 领料记录不全时，前向追溯**只能说明"查到这些"，不能说明"只有这些"**。

把不完整说成完整，是追溯功能最危险的失败方式——用户看到"影响 3 张工单"
会据此决定要不要召回，而真实数字可能是 7。宁可让用户看到一个带警告的
不完整答案，也不要给一个看起来完整的错误答案。

## 替代方案

| 方案 | 为什么不选 |
|---|---|
| 树模型（`material_lot.work_order_id`） | 一批料投多单时第二个值覆盖第一个，数据在写入时就错，且不报错 |
| 序列化到 JSON 字段（`work_order_ids: "[...]"`） | 无法建索引，反查要全表扫；也无法用 SQL 约束保证不重复 |
| 图数据库（Neo4j 等） | 数据量在几十万条量级，SQLite 的两次 JOIN 毫秒级返回；引入图库的运维成本换不来收益 |
