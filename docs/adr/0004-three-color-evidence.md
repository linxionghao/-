# 0004. 三色证据模型：事实 / 引用 / 假设

- 状态：已采纳
- 日期：2026-10-28
- 影响范围：`core/knowledge/prompts.py`、`core/services/chat.py`、`core/services/attribution.py`、`api/routers/chat.py`

## 背景

需求第二个陷阱：LLM 如何避免把检索到的文档内容当成事实结论？

这是 RAG 系统最危险的地方——检索到的文本被拼进提示词后，模型会把"文档说 X"复述成"事实是 X"，再叠加自己的推理，输出一句读起来很确定的结论。在质量场景里，这句话可能被用来判退一批货。

## 决策

把回答里的每一句话归入三类之一，并在**结构与措辞**上强制区分：

| 颜色 | 是什么 | 来源 | 强制形式 |
|---|---|---|---|
| 事实（结构化数据） | 系统里查得到确定值的 | `defect_item`、`work_order` 等表 | 直接陈述 + 数字（"该工单不良 3 件"） |
| 引用（知识库内容） | 文档里写的，**有版本有出处** | `kb_chunk` | 必须带 `[Cn]` 角标，落库时可回溯到 `(doc_name, version, clause, chunk_id)` |
| 假设（推理结论） | 模型/人推出来的 | LLM 或工程师 | 恒带"疑似 / 待验证"，**禁止**"根因已确定" |

落地手段（都不依赖模型自觉）：

1. **提示词只做"引导"**：`SYSTEM_PROMPT` 要求"回答中每个来自资料的结论后面标注 `[Cn]`，无法标注的用'推测'开头"；
2. **引用结构化落库**：SSE 的 `sources` 事件与 `chat_message_citation` 表同时写入 `(source_file, version, clause, chunk_id, score)`。前端渲染引用卡片，后端可审计；
3. **审计规则兜底**：`flag_no_citation` 命中"回答称完成/已确定，但引用数为 0"的消息——即使模型忘了标注，系统也能事后筛出来；
4. **假设的措辞硬编码**：`attribution_order.hypothesis_text` 写入时拼"（待验证）"，8D 导出首行插入 `DRAFT_BANNER` 红条。这两处**不经过模型**，模型无法绕过；
5. **班组长侧连状态文案都不带判定语汇**：`STATUS_TEXT` 只有"待确认缺陷码 / 已提交，待质量工程师判定"，单测断言不含"合格/不合格/判退"。

## 后果

好处：

- "哪句话是查到的、哪句话是猜的"在 UI 上一眼可见（引用卡片 vs 待验证标记）；
- 审计可以量化：`flagged / total` 就是"有多少回答在越界"，可被主管逐条核查；
- 假设措辞与横幅由代码保证，换模型也不会变。

代价：

- 回答会比"直接下结论"啰嗦，需要接受"待验证"这种不干脆的表述；
- 引用角标要求切片带 `clause`（章节标题），切分时不能按固定字数硬切到底（本项目按标题优先切分 + 500 字/80 重叠）。

未来若要改：三色模型已写进 `docs/architecture.md` 与提示词模板，改它等价于改产品语义，必须同步改审计规则与前端渲染。

## 替代方案

| 方案 | 为什么不选 |
|---|---|
| 只在提示词里写"不要编造" | 模型无法判断自己是否在编造；无引用时它照样自信 |
| 让模型输出 JSON 并校验 | 流式体验变差（要等完整 JSON），且模型仍可能把假引用写进 JSON 的 citations 字段 |
| 引用只在前端做（正文里不标） | 正文与引用脱钩，读者无法判断哪一句对应哪条；审计也无从定位 |
| 全部回答都标"待验证" | 等于取消了事实与假设的区别，工程师会忽略这个标记 |
