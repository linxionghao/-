## 什么值得写一条 ADR

满足任一条就写：

- 这个选择**以后有人会想改**（改之前必须先看到当初的理由）；
- 它约束了多处代码（不是局部实现细节）；
- 它有一个"看起来更简单"的替代方案，需要说明为什么不选。

不值得写的：变量命名、目录里放哪个文件、用 for 还是列表推导。

## 模板

```markdown

- 状态：已采纳 / 已废弃（被 NNNN 取代）/ 草案
- 日期：YYYY-MM-DD
- 影响范围：涉及哪些模块

## 背景
当时面临什么问题？有哪些硬约束（技术、人力、交付时间）？

## 决策
具体选了什么。要精确到"能据此写代码"的程度。

## 后果
- 好处：
- 代价：
- 未来若要改，需要动哪些地方：

## 替代方案
| 方案 | 为什么不选 |
|---|---|
```
