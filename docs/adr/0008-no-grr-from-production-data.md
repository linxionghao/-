# 0008. 产线数据不做 GR&R，只做人员读数一致性检查

- 状态：已采纳
- 日期：2026-11-06
- 影响范围：`core/analytics/msa.py`、`core/services/msa.py`、`api/routers/msa.py`、`web/admin/msa.html`

## 背景

MSA 模块做完后，一个很自然的想法是："库里已经有几十万条实测值，
为什么不直接算个 %GRR？"功能都写出来了：按 `(operator, work_order_id)`
折叠成"评价人 × 零件 × 试测"的矩阵，喂给 `msa.report()`。

跑出来的结果是 **%GRR > 90%，判定"测量系统不可接受"**。

这个结论是错的，而且错得很隐蔽——数字算得对，输入不对。

GR&R 要分离三块变差：

```
总变差 = 零件间变差 + 评价人间变差 + 重复性（同一人重复测同一件）
```

产线数据里**第三块不存在**。每件产品只测一次就流走了，没有"同一个人
对同一件测第二次"这回事。折叠时只能用"同一工单、不同时间、不同件"
的差异去顶替"重复性"，而那里面装的是：过程漂移、换刀、换料、
班次温差、来料批间差异。

结果就是：把所有普通原因变差都算进"量具噪声"，%GRR 必然爆表。

## 决策

**不提供"从产线数据算 GR&R"的接口。** 换成它答得了的问题：

> 同一条产线、同一张工单，不同班次的人读数水平一致吗？

判据是均值差的标准误：

```
s_pooled = √( Σ(n_i-1)·s_i² / Σ(n_i-1) )      # 组内合并标准差
se       = s_pooled · √(1/n1 + 1/n2)
z        = |x̄1 - x̄2| / se
```

`z > 3`（可配）即判定"该工单上两人读数显著不一致"。

**`s_pooled` 必须用组内标准差，不能用全局标准差。**
这是整个实现里最容易写错、也最致命的一处：用全局 σ 会把工单之间的
真实差异（10.0mm 与 12.0mm 两种产品）算进噪声，`se` 被撑大，
任何人员偏移都会被掩盖，检查永远返回"一致"——一个给出假安全结论的功能，
比没有这个功能更危险。

测试 `test_pooled_sigma_not_global` 专门守这条：造"工单间差异极大、
组内噪声极小、某人偏移中等"的数据，全局口径 z<3（假安全），
组内口径 z>>3（正确报警）。

三个配套决定：

1. **接口名与返回值都写明"这不是 GR&R"**。`GET /msa/consistency`，
   返回里恒定带 `caveat` 字段。用户会把一致性检查的数字当成 GR&R 去签字，
   所以口径提示不能只写在文档里；
2. **`min_readings >= 3` 门槛**。一个人在同一张工单上只测了 1 件时，
   他的"均值"就是那一个数，和别人的均值比较毫无统计意义；
3. **`GET /msa/advice` 给出正式试验方案**。把"要 GR&R 请重做试验"
   落成一个可点的按钮（10 件 × 3 人 × 3 次、阈值档位、公差带提醒），
   而不是只写一句"数据不足"——后者等于把问题丢回给用户。

## 后果

- 好处：给的是**真的**结论。它不需要额外试验就能抓出"某人总是偏高 0.01mm"
  这类真实问题，而这些问题的处置成本远低于换量具；
  同时 GR&R 的正规路径没被堵住，只是要求按规程做试验。
- 代价：少了一个看起来"很智能"的功能。演示时不能点一个按钮就出 %GRR，
  需要先有试验数据。这是有意的取舍：**能算 ≠ 该算**。
- 未来若要改：`consistency_check()` 的判据可以升级（比如改成 ANOVA 的
  人员效应检验），但"不拿产线数据冒充 GR&R"这条不变。

## 替代方案

| 方案 | 为什么不选 |
|---|---|
| 照原样算，但结果标注"仅供参考" | "仅供参考"四个字挡不住它被截图写进报告；结论错的功能不该上线 |
| 算出来但只在 %GRR 很低时才显示 | 门槛怎么定都是拍脑袋；而且低了不代表算对了 |
| 用嵌套方差分析（零件嵌套在工单里） | 方向对了，但产线数据里"同一件测两次"仍然不存在，重复性项无解 |
| 要求产线每件测两次 | 会改变现场作业方式，成本远高于做一次正式 GR&R 试验 |
