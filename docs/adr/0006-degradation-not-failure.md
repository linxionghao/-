# 0006. 降级不是失败：HTTP 200 + degraded 标记

- 状态：已采纳
- 日期：2026-10-30
- 影响范围：`core/services/errors.py`、`core/services/chat.py`、`api/routers/chat.py`、`web/chat.html`

## 背景

本系统有三条会"部分失效"的外部能力：LLM 生成、向量服务、流式超时。它们的共同点是——**失效后系统仍然有用**：

- 没有 LLM：检索与引用照常，工程师能自己看依据；
- 没有向量服务：BM25 关键词检索照常；
- 流式超时：已生成的部分正文 + 完整引用仍然可读。

如果这些情况一律返回 5xx，前端只能显示"服务异常，请重试"，而实际上用户想要的信息有一半已经拿到了。这会训练用户"看到错误就刷新"，把可用信息也丢掉。

## 决策

把"能力降级"与"请求失败"在协议层分开：

| 情况 | HTTP | body | 前端表现 |
|---|---|---|---|
| 请求本身有问题 | 4xx | `code: 4xxxx`，`data: null` | 红色错误条 + 中文建议 |
| 能力降级 | **200** | `code: 0`，`data.degraded = {code, message}` | 黄色提示条，内容照常渲染 |
| 配置里本来就没开 | 200 | `degraded: null` | 无任何提示 |

三个降级码：

| 码 | 含义 | 用户看到的文案 |
|---|---|---|
| 50001 | 向量服务不可用，已退回关键词检索 | 检索已降级为关键词匹配，结果可能不够精准 |
| 50002 | LLM 不可用 | 大模型不可用，仅展示检索到的依据 |
| 50401 | 流式超时（已产出部分正文） | 大模型响应超时，回答可能不完整 |

配套约定：

- `chat_message.degraded / degraded_code / degraded_reason` 三列落库，事后可统计"降级发生率"；
- 降级消息**不会被审计误报**为"无引用却称完成"——因为降级本来就没有正文（`audit.flag_message` 对降级消息特殊处理）；
- 降级不是"静默"：状态条必须出现，但用黄色而非红色。

## 后果

好处：

- 没有 API Key 也能完整演示（`scripts/demo_closed_loop.py` 第 2 步就是靠这个跑通的）；
- 用户拿到"一半有用的东西"而不是"一个报错"；
- 降级可统计、可审计，不是"偶然现象"。

代价：

- 前端要区分三态（成功 / 降级成功 / 失败），比"非 0 即错"复杂；
- 团队新人容易把"配置关闭"也写成降级——本项目在 `docs/test-plan.md` 与测试里专门钉了这条（`meta["degraded"] is False`）；
- 500 系列码被用作业务码而非 HTTP 状态，对不熟悉本项目的外部对接方需要文档说明（`docs/api.md` 第 5 节有映射表）。

未来若要改：三个码的语义已经写进 `errors.py` 的 `MESSAGES` 与前端判断逻辑，改语义等于改产品行为，需同步 ADR。

## 替代方案

| 方案 | 为什么不选 |
|---|---|
| 降级也返回 5xx | 前端无法区分"重试有用"和"重试也没用"，用户会丢掉已拿到的引用 |
| 返回 200 但不标注降级 | 用户以为拿到的是完整答案，在质量场景里比报错更危险 |
| 静默用缓存兜底 | 缓存内容可能与当前 `as_of` 视角不符，等于制造不可解释的旧结论 |
| 让前端探测 `/health` 判断 | 健康检查通过 ≠ 本次请求没降级（Key 突然失效、配额用尽都发生在请求内） |
